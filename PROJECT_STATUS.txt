2. WHAT THE PRODUCT IS
-------------------------------------------------------------------------------

A native iPhone app that stores a complete 36-week full-distance triathlon
training plan, maps it onto real calendar dates from either a start date or a
race date, answers "what do I do today?", and sends calm local reminders.

Design intent, from plan.txt:
  - Feels like a first-party Apple app: quiet, legible, native, accessible.
  - Calm, not gamified. No confetti, streak pressure, neon, or shame language.
  - Safety over completion statistics. Never encourages stacking missed hard
    sessions to protect a percentage.
  - Offline and private by default. No account, no analytics, no data leaves
    the device.
  - Not medical or coaching advice; educational organiser only.

Intended first user: a 20-year-old athlete training ~9 months for a first
full-distance triathlon, with the goal of finishing safely, not racing fast.

Working product name "Endurance" is isolated to two places (project.yml
PRODUCT_NAME, and EnduranceDomain.productName) so a rename is cheap.

5. ARCHITECTURE — THE KEY DECISION
-------------------------------------------------------------------------------

The load-bearing architectural choice is that EnduranceDomain is Foundation-only
and depends on nothing Apple-UI-shaped. Consequences:

  - The riskiest logic (DST and leap-year date math, the 64-notification budget,
    plan validation, unit conversion, progress aggregation, export round trips)
    is testable WITHOUT Xcode, on any Swift toolchain, in under a second.
  - The same core can be consumed unchanged by the iOS app, the future watchOS
    app, widgets, and App Intents. No core logic lives in the app target.
  - Domain value types stay the single source of truth. The SwiftData layer
    stores query columns (date, week, status) plus an encoded payload of the
    domain struct, rather than duplicating every field — this avoids drift
    between the persisted schema and the domain model.

Views never touch ModelContext. All mutation goes through WorkoutStore, which
keeps persistence, notifications, and the shared widget snapshot consistent.

Layered identity (WorkoutIdentity) separates plan / template / scheduled /
execution / external-provider IDs, so a workout survives rescheduling, HealthKit
import, watch completion, and eventual Garmin/Strava sync without ever being
identified by title+date.

6. TRAINING PLAN CONTENT
-------------------------------------------------------------------------------

Generated deterministically by PlanGenerator, validated, and committed as JSON
(~1.0 MB). Regeneration is byte-reproducible and a test asserts the committed
file stays in sync with the generator.

  schemaVersion 1
  36 weeks / 252 days / 382 workouts

  Foundation              weeks  1-4
  Base 1                  weeks  5-8
  Base 2                  weeks  9-12
  Build 1                 weeks 13-16
  Build 2                 weeks 17-20
  Endurance specificity   weeks 21-24
  Race-specific build     weeks 25-28
  Peak                    weeks 29-33
  Taper                   weeks 34-35
  Race week               week  36

Content tests assert: phases tile all 36 weeks; long runs never exceed ~2.5h
(no full-marathon training run); every non-recovery week from base onward has a
weekend brick; race week ends with a race-day session; preparation and fueling
guidance attach only to long/brick/race sessions.

Sourcing and the reasoning behind the periodisation are cited in
TRAINING_SOURCES.md. Fueling and hydration are framed as configurable targets
and practice recommendations, never as personalised medical nutrition advice.

7. WHAT CHANGED THIS SESSION (commit 795b5ab)
-------------------------------------------------------------------------------

Branch: build/first-xcode-build   (branched from main at f508f03)

Environment unblocking (the real blocker, and it was not what the docs claimed):
  Xcode 26.6 was already installed at /Applications/Xcode.app. The problems were
  that (a) xcode-select still pointed at CommandLineTools, (b) the Xcode license
  had never been accepted, and (c) Xcode 26 ships WITHOUT iOS platform support,
  requiring a one-time ~8 GB `xcodebuild -downloadPlatform iOS`. Until all three
  were resolved there were zero usable build destinations, and `swift test`
  failed with "no such module 'Testing'" because swift-testing resolves through
  the Xcode toolchain, not CLT.

Three code fixes — the complete set of first-build failures across ~2,500 lines:

  1. NotificationScheduler.swift — Swift 6 strict concurrency.
     Awaiting `sync` from the main actor sent a non-Sendable object across an
     isolation boundary. The class is now @MainActor. But
     UNUserNotificationCenterDelegate is NOT @MainActor and its parameters are
     not Sendable, so isolating the class alone traded one error for four; the
     two delegate witnesses are therefore `nonisolated` and hop to the main
     actor themselves.

  2. NotificationSettingsView.swift — SwiftUI API misuse.
     `Section("Timing") { ... } footer: { ... }` is not a real initializer; a
     string title and a footer are mutually exclusive. Replaced with the
     explicit header:/footer: form.

  3. Info.plist — missing standard bundle keys.
     No CFBundleIdentifier, so the Simulator refused to install the app
     ("Missing bundle ID"). XcodeGen injects these only under
     GENERATE_INFOPLIST_FILE, which this target does not use. Added
     CFBundleIdentifier, CFBundleExecutable, CFBundlePackageType,
     CFBundleInfoDictionaryVersion, CFBundleDevelopmentRegion, and switched
     CFBundleName to $(PRODUCT_NAME).

Documentation corrected: README.md and LIMITATIONS_AND_NEXT_STEPS.md both
asserted a headless environment with no Xcode and listed the six screens as
unimplemented. Both were false. CHANGELOG.md gained a Stage 2b entry.

10. TOOLCHAIN AND HOW TO BUILD
-------------------------------------------------------------------------------

Verified working configuration:
  macOS (Darwin 25.5.0), Xcode 26.6 / build 17F113
  iOS 26.5 SDK, iOS 26.5 Simulator runtime installed
  Swift 6.3.1, XcodeGen 2.46.0
  Deployment target iOS 18.0, Swift 6 language mode, strict concurrency complete

One-time machine setup (only needed on a fresh Mac):
  sudo xcode-select -s /Applications/Xcode.app/Contents/Developer
  sudo xcodebuild -license accept
  sudo xcodebuild -runFirstLaunch
  xcodebuild -downloadPlatform iOS      # ~8 GB, Xcode 26 has no iOS support
  brew install xcodegen                 #         built in

Order matters: xcode-select must come first, because `xcodebuild` does not exist
in the CommandLineTools toolchain.

Domain tests only (fast, no Simulator):
  cd EndurancePackages && swift test

Regenerate the 36-week plan:
  cd EndurancePackages && swift run enduranceplan

Full build and test:
  xcodegen generate
  xcodebuild test -project Endurance.xcodeproj -scheme Endurance \
    -destination 'platform=iOS Simulator,name=iPhone 17'

Run it and look at it:
  open -a Simulator
  xcrun simctl install booted <DerivedData>/Build/Products/Debug-iphonesimulator/Endurance.app
  xcrun simctl launch booted com.example.endurance
  xcrun simctl io booted screenshot shot.png

Physical device: open Endurance.xcodeproj, set a development team and a unique
bundle identifier under Signing & Capabilities, then run. A free Apple ID works
but the build expires after ~7 days. TestFlight needs the paid Apple Developer
Program. See README.md.

13. RISKS AND JUDGEMENT CALLS
-------------------------------------------------------------------------------

  The app has never been used. It compiles and launches, which is a real
  milestone but a low bar. The gap between "renders onboarding" and "correctly
  schedules 382 workouts across DST boundaries and cancels the right
  notifications" is entirely unmeasured at the UI level. The domain logic
  underneath it is well tested, which is the reason for optimism, but the
  wiring between them is not.

  Localization debt is compounding. Every screen added before the String
  Catalog exists makes the eventual migration larger. Section 28.18 anticipated
  exactly this and was not followed.

  Onboarding currently asks for preferred long-session and rest days and then
  ignores them. A user would experience this as a bug.

  Notification behaviour is the most complex part of the product (stable IDs, a
  rolling window under a hard 64-request system cap, cancellation on
  completion, regeneration on date change, deep links). It is thoroughly
  unit-tested as pure logic and completely unobserved in practice.

  The 36-week plan is a single generic finish-goal plan. It is personalised only
  through scheduling. Onboarding's capability questions feed warnings and future
  adaptation but deliberately do not silently rewrite the plan.
